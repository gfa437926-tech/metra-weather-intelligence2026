# METRA — مراجعة اتساق تصميم قاعدة البيانات الجديدة

**التاريخ:** 2026-11-14  
**الحالة:** مراجعة هندسية للوثائق؛ لا DDL مطبق ولا اتصال بقاعدة مستضافة.  
**النطاق:** نموذج Greenfield مستقل، دون استيراد بيانات أو مخطط من أي قاعدة سابقة.

## 1. نتيجة المراجعة

الوثائق الحالية تصلح أساساً معمارياً، لكنها **ليست جاهزة بعد لتوليد migrations كاملة**. ظهرت فجوات تكامل مرجعية وأمنية يجب إغلاقها في التصميم قبل تحويله إلى DDL. لا يجوز وصف المخطط بأنه نهائي أو قابل لإعادة البناء قبل إنشاء migrations وتشغيل اختبارات فعلية على بيئة CI معزولة.

## 2. عيوب اتساق يجب إصلاحها قبل DDL

| # | المجال | الملاحظة | المعالجة المطلوبة |
|---:|---|---|---|
| 1 | IAM / النطاق | `role_assignments` و`permission_grants` تملكان معرفات نطاق مستقلة، لكن FK المفرد لا يضمن أن الوحدة أو المحطة تتبع الجهة نفسها أو عضوية المستفيد. | إضافة مفاتيح فريدة مركبة ومفاتيح أجنبية مركبة تربط (organization_id, unit_id) و(organization_id, station_id)، والتحقق من أن نطاق التعيين متوافق مع عضوية المستخدم. |
| 2 | IAM / العضوية | `memberships.organization_unit_id` قد تشير إلى وحدة تابعة لجهة أخرى. | FK مركب على (organization_id, organization_unit_id)، مع السماح بـ NULL للوحدة عند العضوية على مستوى الجهة. |
| 3 | القيم العلمية | `value_kind` يذكر decimal/integer/text/boolean/code بينما `observations.values` لا يعرّف عموداً مستقلاً للرمز. | إضافة `value_code` أو اعتماد تمثيل code موثق؛ وفرض CHECK يضمن وجود قيمة واحدة فقط من الأنواع المسموح بها، مع مطابقة النوع لتعريف البارامتر. |
| 4 | القيم العلمية | التطابق بين نوع القيمة في تعريف البارامتر ونوع العمود لا يمكن ضمانه بـ CHECK عادي يعبر جدولاً آخر. | فرض التطابق داخل دالة/إجراء كتابة خادمي موثوق أو trigger ضيق ومختبر؛ لا تعتمد على تحقق Flutter. |
| 5 | قاموس البارامترات | صياغة التفرد في عمود `code` غير واضحة بين UQ(code) وUQ(code, definition_version). | اعتماد UNIQUE(code, definition_version) صراحةً، وإضافة قواعد عدم تداخل فترات الإصدارات للرمز نفسه عند الحاجة. |
| 6 | المحطات | `station_capabilities.capability_code` نص حر بينما الوثائق تصفه قاموساً معتمداً. | إنشاء `ref.station_capabilities` أو كيان مرجعي مكافئ وربط السجل به بمفتاح أجنبي. |
| 7 | المواقع | لا يوجد تعريف كامل لشرط تزامن latitude/longitude ولا آلية منع تداخل فترات الموقع في DDL. | CHECK يفرض وجود الإحداثيين معاً أو غيابهما معاً؛ واستخدام exclusion constraint على فترة زمنية نصف مفتوحة لكل محطة بعد تثبيت امتداد GiST المعتمد. |
| 8 | التنبؤات | `forecast_points` لا يحدد بشكل تنفيذي XOR بين إحداثيات النقطة ومرجع الخلية، كما أن علاقة provider في forecast_run وingestion_run غير محمية من اختلاف المزودين. | إضافة CHECK مكاني، ومفاتيح فريدة/مركبة تضمن أن provider_id في السجلين متطابق. |
| 9 | التنبؤات | نوع القيم في forecast_points غير موحد مع `value_kind` المرجعي ولا يوضح هل القيم Boolean/Code مسموحة. | قصرها على الأنواع التي يثبتها عقد المزود أو إضافة الأعمدة/القيود المقابلة؛ لا نفترض أن كل التنبؤات رقمية قبل مراجعة العقد. |
| 10 | المراجعات | `registration_decisions` و`review_decisions` لا يحددان سياسة إعادة المحاولة/تعدد القرارات للمرحلة أو revision. | إضافة رقم محاولة/نسخة متوقعة ومفاتيح تفرد مناسبة، مع معاملات انتقال حالة ذرية واختبارات actor separation. |
| 11 | الملفات | جداول الملفات تحفظ metadata فقط، لكن دورة الفحص والحجر والربط والحذف من Storage غير محددة تنفيذياً. | اعتماد state machine للرفع والفحص، وسياسة bucket خاصة، ومنع الوصول إلى quarantined/deleted، ومزامنة حذف موثوقة. |
| 12 | التدقيق | وصف append-only موجود، لكن لا توجد آلية DDL تمنع UPDATE/DELETE أو صلاحيات إدخال محددة. | سحب UPDATE/DELETE من أدوار التطبيق، وقصر INSERT على دور/دالة موثوقة، وإضافة اختبارات سلبية؛ لا تعتمد على naming convention. |

## 3. ضبط النطاق التنفيذي

لتجنب إنشاء قاعدة ضخمة قبل وجود عقود علمية أو مزودين، يكون التنفيذ على مراحل:

### المرحلة A — أساس MVP

- الهوية وملفات المستخدمين والجهات والعضويات.
- الأدوار والصلاحيات والنطاقات والتفويضات.
- دليل المحطات الجديد ومراجعاته ومواقع المحطات.
- قاموس مرجعي فارغ/محايد من دون اختلاق بارامترات أو وحدات علمية.
- الرصد اليدوي وإصداراته وقرارات مراجعته، بعد تعريف عقد النموذج العلمي.
- التدقيق والملفات وفق سياسة أمنية محددة.

### المرحلة B — مزودات الطقس

لا تدخل في baseline الأولى إلا بعد توثيق عقد المزود، ومفاتيح إزالة التكرار، وتوقيت الإصدار، وتغطية النقاط/الخلايا، ووحدات كل حقل، وحقوق تخزين payload الخام.

### المرحلة C — التنبيهات والمناخ والتحليلات

تبقى خارج DDL الأولي حتى تتوفر مصادر رسمية مرخصة وعقود علمية وخوارزميات قابلة لإعادة الإنتاج. لا تعرض الواجهة أي خدمة من هذه الخدمات على أنها متصلة قبل تنفيذها واختبارها.

## 4. قرارات هندسية معتمدة ضمن هذه المراجعة

1. لا نقل ولا مزامنة ولا استنساخ من قاعدة قديمة، لا للبيانات ولا للمخطط ولا لتاريخ migrations.
2. لا تُنشأ بيانات محطات حقيقية من التخمين. بيانات الاختبار الاصطناعية تكون منفصلة وموسومة.
3. يظل .NET API هو الحد الموثوق المستهدف للعمليات الحساسة. يمكن إبقاء Edge Functions الحالية كطبقة انتقالية مؤقتة فقط، مع عقد واحد واضح للصلاحيات والمعاملات وخطة إزالة/نقل موثقة؛ لا يسمح بتكرار منطق العمل في طبقتين.
4. لا تُخزن كلمات المرور أو مفاتيح الخدمة أو الأسرار في الجداول أو التطبيق أو Git.
5. كل جداول التطبيق المكشوفة عبر Data API تحتاج RLS وسياسات مفصلة؛ الجداول الداخلية غير مكشوفة افتراضياً.
6. لا SECURITY DEFINER إلا لضرورة موثقة، مع search_path ثابت، وفحص actor، وسحب EXECUTE من PUBLIC، واختبار أمني.
7. لا يُنشأ مستخدم مدير افتراضي أو صلاحية شاملة أو grant أولي عشوائي.
8. لا تُنشر migrations إلى المشروع المستضاف قبل مراجعة مستقلة وموافقة صريحة.

## 5. مسار التنفيذ السحابي دون الاعتماد على جهاز المستخدم

يمكن تشغيل بيئة الاختبار على GitHub-hosted runner باستخدام Docker وSupabase CLI مثبتين ومثبتَي الإصدار داخل GitHub Actions. تكون البيئة مؤقتة لكل تشغيل، ولا تحتاج إلى تثبيت أي برنامج على جهاز المستخدم.

خطوات CI المطلوبة:
1. تثبيت نسخة Supabase CLI محددة والتحقق من إصدارها.
2. إنشاء مساحة عمل Greenfield منفصلة عن `supabase/migrations` الحالية.
3. توليد أسماء ملفات migrations بواسطة `supabase migration new`، وعدم اختراع timestamps يدوياً.
4. تشغيل Supabase local stack داخل runner فقط.
5. تنفيذ reset على قاعدة اختبار فارغة مرتين.
6. تشغيل اختبارات قيود PostgreSQL وRLS وBOLA/IDOR وفصل المراجعين.
7. حفظ schema snapshot ونتائج الاختبارات كـ CI artifacts.
8. منع workflow من استخدام `--remote` أو أسرار Supabase المستضاف.

**قيد مهم:** لا يمكن اعتبار هذا المسار منفذاً حتى يضاف workflow ويظهر تشغيل ناجح فعلياً. لا يوجد في هذه المراجعة ادعاء بأن CLI أو Docker قد شُغّلا.

## 6. بوابة الخروج إلى التنفيذ

تعد المرحلة A جاهزة لتوليد DDL فقط عندما:
- تُغلق فجوات الاتساق أعلاه في ERD والقاموس.
- تكون قواعد النطاق المركب موثقة وقابلة للاختبار.
- يعتمد عقد الرصد العلمي الأولي أو يتم تأجيل جداول القيم إلى مرحلة لاحقة.
- تحدد سياسة RLS وGRANT لكل جدول.
- تنجح إعادة البناء مرتين في CI على قاعدة فارغة.
- تنجح اختبارات الوصول المسموح والممنوع.

حتى ذلك الحين، تظل قاعدة Supabase المستضافة دون تعديل، ولا يعلن عن اكتمال قاعدة البيانات.
