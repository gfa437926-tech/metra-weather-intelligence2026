## 1. ضوابط API والمعاملات

- .NET API هو الحد الموثوق للعمليات الحساسة، ويشتق actor من JWT موثوق.
- حفظ المسودة والإرسال والقرار وتغيير الحالة وحدث التدقيق تتم بمعاملة ذرية.
- لا يثبت station_id أو reviewer_id أو role_id المرسل من Flutter أي صلاحية.
- كل عملية قراءة/كتابة مقيدة بالجهة والمحطة المسموح بهما؛ اختبارات BOLA/IDOR إلزامية.
- idempotency ومقارنة expected revision/state تمنع تكرار الطلب والقرارات المتزامنة.
- بيانات الاختبار الاصطناعية تحمل وسم demo واضحاً ولا تختلط ببيانات الإنتاج.

## 2. فجوات قبل migrations

1. قاموس علمي للبارامترات والوحدات والدقة والمدى وطرق القياس.
2. العقد النهائي لنماذج الرصد وتوقيتاتها والتعامل مع الوقت المحلي وUTC.
3. قائمة الأدوار والصلاحيات ونطاقاتها والفصل بين المراجعين.
4. مصدر دليل المحطات الجديد وآلية توثيق المواقع والارتفاعات.
5. مزود التنبؤ المعتمد وشروطه ومعدل الجلب وسياسة raw payload.
6. أنواع الملفات والحجم والفحص والاحتفاظ.
7. سياسات الاحتفاظ والتصدير والنسخ الاحتياطي والتدقيق.

## 3. إعادة البناء من الصفر دون المساس بالتطبيق الحالي

المستودع يحتوي بالفعل على `supabase/migrations` مرتبطة بخط التطبيق الحالي. لا تعدّل أو تحذف أو تعيد ترقيم migrations التاريخية. بعد اعتماد ERD والقاموس، أنشئ baseline مستقلة لاختبار disposable database بمسار/config مستقل موثق. يجب إثبات أن قاعدة اختبار فارغة تُبنى بالكامل دون الاتصال بقاعدة الإنتاج ودون استيراد بيانات قديمة.


## 4. ملاحظة توافق معماري من فحص المستودع

README الحالي يوثق أن وظائف التسجيل ودليل المحطات ومراجعتها والرصد تعمل عبر Supabase Edge Functions في التنفيذ الموجود. في المقابل، قرار المعمارية المستهدف للمشروع يضع .NET API كحد التطبيق الموثوق. لذلك يجب أن تحدد مراجعة المعمارية خطة انتقال واضحة: إما إبقاء Edge Functions الحالية كطبقة انتقالية مع نقل use cases تدريجياً إلى .NET، أو اعتماد Edge Functions نهائياً بعد مراجعة أمنية صريحة. لا يجوز أن تعمل طبقتان كحدود ثقة متوازية بلا مالك واضح للمعاملات والصلاحيات. لا يغيّر هذا المستند التنفيذ الحالي ولا ينشر أي خدمة.
